## Часть 3. Композиционный анализ проектов на C/C++, PURL, CPE
В C/C++, как правило, нет удобного списка зависимостей, аналогичного, например, `go.mod` или `requirements.txt`.

В ходе выполнения заданий 3 части у нас должны получиться следующие артефакты работы:
- скриншоты выполнения пунктов задания.
- файлы bom.json для обоих приложений.
- фрагменты bom.json с описанием разбираемых сработок, пример их исправления.
- фрагмент bom.json qemu с добавленным cpe.

### cdxgen, grype
Соберите SBOM проекта libvirt с помощью инструмента `cdxgen` (возможно придется использовать доп. флаги для более глубокого поиска). Проанализируйте его с помощью `trivy`. Оцените вывод. Повторите анализ того же SBOM-файла с помощью другого опенсорсного инструмента - `grype`. В нем для поиска уязвимостей используется Common Platform Enumeration (CPE, [стандарт](https://nvlpubs.nist.gov/nistpubs/Legacy/IR/nistir7695.pdf)). Попробуйте с помощью grype автоматически сгенерировать CPE для всех зависимостей, у которых их нет, с помощью `--add-cpes-if-none`. Как можно было бы улучшить SBOM, чтобы генерировать меньше сработок?

Проведите аналогичный анализ проекта qemu. Попробуйте зафиксировать конкретную версию компонента qemu.

### PURL, CPE
Как мы могли заметить, cdxgen генерирует описание пакетов в формате purl, а grype ожидает их в формате cpe. Попробуйте самостоятельно добавить к компоненту qemu поле "cpe" с оформленным cpe. Примеры того, как выглядит cpe для qemu, можно найти в описании любой CVE для qemu в базе NVD. Проверьте, находятся ли теперь сработки SCA без флага `--add-cpes-if-none`. Что имеет приоритет при анализе grype - purl или cpe?
