## Проект. Оркестратор статических анализаторов

В sast-1 и sast-2 мы запускали Cppcheck и Clang Static Analyzer вручную. Теперь напишем небольшое CLI-приложение, которое будет запускать эти анализаторы с настройками из YAML/TOML и сохранять результаты в формате SARIF. Язык реализации можно выбрать самостоятельно.

### Общая часть

Реализуйте запуск анализа одной командой, например:

```shell
python -m sast_project scan config.toml
```

В конфигурации задаются каталог проекта, команды сборки, настройки анализаторов и каталог результатов. Пример:

```toml
language = "C"
work_dir = "./libtiff"
output_dir = "./reports"
build_command = """
  ./configure
  make clean
  make -j2
"""

[sast]
scanners = ["cppcheck", "clangsa"]

[sast.scanner_options.cppcheck]
timeout = 120
paths = ["libtiff", "tools"]
enable = ["warning", "performance"]

[sast.scanner_options.clangsa]
timeout = 600
```

`work_dir` — рабочий каталог, `sast.scanners` — список запускаемых анализаторов, `scanner_options` — их настройки. Пути `work_dir` и `output_dir` считайте относительно файла с конфигом, пути Cppcheck — относительно `work_dir`. Анализаторы и зависимости для сборки устанавливаются заранее.

Приложение должно:

- Последовательно/параллельно запускать включённые анализаторы с указанными настройками.
- Сохранять результаты в формате SARIF. Для Cppcheck используйте `--output-format=sarif`, для scan-build `-sarif`. При этом scan-build будет создавать несколько файлов во временной директории, их нужно "склеить" в один документ.
- Для Clang (`clangsa`) выполнять `build_command` через `scan-build` в каталоге `work_dir`. Это shell-скрипт с остановкой при первой ошибке; он должен включать подготовку, очистку и сборку проекта, как в части 2.
- Сообщать об ошибочном TOML/YAML, отсутствии программы, ошибке сборки и превышении таймаута. Ошибка одного анализатора не должна мешать запуску другого.
- Сохранять команды, логи и краткую сводку `summary.json`: статусы анализаторов, пути к отчётам и результаты своего варианта.

### Варианты

Выполните **один назначенный вариант**. Во всех вариантах обрабатывается только SARIF Cppcheck. SARIF — формат результатов анализа на основе JSON: срабатывания находятся в `runs[].results[]`. Для обработки понадобятся правило, файл, строка, сообщение и уровень срабатывания. Структуру можно изучить по полученному отчёту и [спецификации SARIF](https://docs.oasis-open.org/sarif/sarif/v2.1.0/os/sarif-v2.1.0-os.html).

1. **Сравнение запусков.** Добавьте в TOML/YAML путь к предыдущему SARIF-отчёту. Сравните его с текущим и сохраните списки новых, исчезнувших и сохранившихся срабатываний. Совпадение определяется по правилу, относительному пути и строке.

2. **Подавление срабатываний.** Добавьте в TOML/YAML исключения по путям. Применяйте их после анализа: сохраняйте списки активных и подавленных срабатываний, либо вырезайте прямо из SARIF.

3. **Проверка порогов.** Добавьте в TOML/YAML допустимое количество срабатываний по уровням SARIF, например `error = 0` и `warning = 5`. При превышении порога укажите причину и верните код `1`. Равенство порогу допустимо; уровни без порога не ограничиваются. Покажите успешную проверку и превышение.

### Проверка и сдача

Запускайте на LibXfont из sast-1 только cppcheck, а на libtiff из sast-2 оба анализатора. Для одной библиотеки сохраните анализ до и после исправления целевой уязвимости и объясните исчезновение сработки. Можно использовать уже подготовленное исправление; подавление сработки исправлением не считается.

Свой вариант можно проверять на небольшом тестовом примере.

В PR должны находиться:

- исходный код приложения;
- README с установкой, запуском, номером варианта и описанием формата конфига;
- примеры конфигураций и исходников для проверки варианта;
- `submission/artifacts/` с результатами запусков.

Дополнительно, для получения бонусных баллов можно:
- реализовать ещё один вариант, помимо своего;
- подключить дополнительный анализатор;
- все что звучит для вас интересно.
